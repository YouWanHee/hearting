# Fleet 부모 연결과 실행 관측 정비

2026-09-14. 이 변경은 Fleet의 관측과 표시를 수정한다. 실행 중인 작업의
부모 신원, 완료 전달 대상, 감독 상태, 재시도 권한을 변경하지 않는다.

## 부모가 살아 있는데 orphan으로 표시

관리형 Codex의 app-server는 fork 이후 thread를, 화면에 보이는 TUI는
이전 thread를 가질 수 있다. 기존 수집기는 새 thread의 숨겨진 app-server만
찾고 부모를 orphan으로 확정했다. 렌더러에 있던 같은 관리형 세션 디렉터리
연결 코드는 이미 내려진 orphan 판정 때문에 실행되지 않았다. 기존 테스트는
수집기를 거치지 않고 렌더러만 호출하여 이 충돌을 놓쳤다.

부모 표시 결정은 수집기에 모았다. 정확한 가시 thread를 우선하고, 없거나
동일 관리형 세션의 숨겨진 app-server만 있으면 유일한 TUI 연결을 사용한다.
렌더러의 별도 managed-parent 귀속 분기를 제거했다. 복수 후보, 다른 관리형
세션, 죽은 정확한 부모, plugin queue는 임의로 붙이지 않는다. 잠깐 수집에서
빠진 부모의 기존 유예는 유지하며, 원장의 parent_sid는 수정하지 않는다.

실제 수집 snapshot을 설치본과 수정본의 수집기→렌더러에 각각 재생했다.
같은 작업이 수정 전에는 orphan, 수정 후에는 원래 부모 아래에 표시됐다.
완료 전달에 쓰는 원래 부모 ID는 양쪽에서 같았다.

## 테스트를 실행하는데 idle만 표시

Codex 실행용 sandbox가 `codex-*` 보조 프로세스로 제외되어 그 아래 bwrap,
shell, 검증 lease와 실제 테스트가 관측되지 않았다. 또한 작업 행은 실행 정보를
붙이기 전에 상태를 판정했고, 감독자의 `parked-supervised`를 곧바로 idle로
표시했다. native 상태나 timestamp가 없는 세션도 실제 실행 증거를 소비하지 못했다.

실행 wrapper는 제한된 깊이 안에서 통과하며 wrapper 자체를 실행 증거로
승격하지 않는다. 선택 경로의 모든 PID/start/부모 관계를 앞뒤로 확인하고,
등록 작업은 attempt 태그도 일치해야 한다. 읽기 실패·PID 재사용·재부모화·외부
attempt는 작업으로 결론 내리지 않는다. 기존 상시 helper, 시작 시점의 MCP,
wait primitive와 뒤의 활동으로 background임이 입증된 프로세스는 제외한다.

정확한 실행 증거를 작업 행에 먼저 결속한 뒤 공통 classifier를 한 번 호출한다.
모델/감독자의 대기 상태와 실제 도구 실행을 함께 보존하여, 살아 있는 도구가
입증되면 화면은 working을 표시한다. 터미널 완료 관측은 이 표시로 뒤집지 않는다.

## 검증과 한계

- 부모 연결: 수집기부터 렌더러까지의 회귀, 역순 프로세스 목록, 오래된 TUI ID,
  중복 후보, 잘못된 관리형 디렉터리, 부모 종료와 유예를 검사했다.
- 실행 관측: 보고된 sandbox 계층을 재생하고 PID 재사용·다른 attempt·관측 실패·
  빈 wrapper·상시 helper·wait primitive를 검사했다. 별도 로컬 실제 프로세스로
  sandbox→bwrap→node 계층을 만들어 정확한 소유 증거와 정상 종료도 확인했다.
- 제품 테스트는 재실행하지 않았다. 당시 전체 snapshot이 없는 사례에 현재
  감독 상태를 소급 적용하지 않는다. 임의 서비스와 foreground 작업을 이름만으로
  완전히 구별한다고 주장하지 않는다. 외부/분리 실행에 대한 감시 책임은 별도다.

집중 검증은 50개 테스트와 공식 격리 runner의 관련 8개 묶음에서 통과했다.
마지막 실행 결속 수정의 2개 묶음도 재검증했다. 넓은 검사 100개 묶음은
91 PASS, 기존 import 오류 6 KNOWN-FAIL, 기존 baseline 대비 1 XPASS였다.
새 테스트의 mirror 누락은 정상 생성기로 수정했고 mirror 재검증은 PASS다.
refresh의 시간 민감 assertion 1건은 단독 공식 재검증에서 PASS였으며, 최초
실패 원인을 확정했다고 주장하지 않는다. 사용량 조회 테스트는 최초 120초
예산을 넘겼지만 변경 전 334.95초, 변경 후 343.06초에 각각 PASS였다.
따라서 전체 Fleet이 처음부터 모든 검사를 통과했다고 보고하지 않는다.
