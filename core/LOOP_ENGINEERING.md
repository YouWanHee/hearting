# 하팅 개발 철학 — Loop Engineering

하팅은 사용자의 의도가 검증된 결과와 인수까지 이어지도록 작업의 루프를
책임진다. 실행을 제한하는 장치의 수가 아니라, 정상·실패·중단 상황에서도
작업을 잃지 않고 마무리하는 능력으로 평가한다.

여기서 Loop Engineering은 하팅의 개발 원칙을 부르는 이름이다. 외부의 특정
방법론을 채택했다는 뜻이 아니다. 새 작업마다 읽거나 제출할 절차를 추가하지
않는다. 유지보수자가 구조와 변경의 타당성을 판단할 때 적용한다.

## 1. 기능의 단위는 끝까지 이어지는 책임이다

`의도 → 실행 → 관측 → 결과 확정 → 후속 실행 또는 복구 → 마무리 → 인수`

각 전이의 결정권자는 하나여야 한다. 여러 관측자가 증거를 수집할 수 있어도,
각자 성공을 뒤집거나 재시도를 만들면 안 된다. 작업의 책임자가 바뀔 때는
무엇을 넘겼고 누가 받았는지가 남아야 한다. 원 책임자는 인수 확인 전까지
의무를 버리지 않는다. 프로세스 종료, 보고서 작성, 작업 완료, 사용자 통보는
서로 다른 사실이다.

| 결정 | 끝까지 이어져야 하는 책임 |
|---|---|
| 실행 허용 | 정확한 실행 정체성과 수명 관리자를 연결한다. |
| 실행 보류·거부 | 원인, 남은 의무, 담당자와 지원되는 다음 행동을 반환한다. |
| 완료 확정 | 내용·증거·정리 상태를 확인하고 확정한 결과를 보존한다. |
| 재시도 | 기존 결과와 실제 정리를 먼저 확인하고 중복 실행을 막는다. |
| 관측 실패·정체 | 미확정을 보존하며 재관측 또는 사람에게 넘기는 책임을 유지한다. |
| 마무리 | 후속 단계, 산출물 봉인, 실패 정리의 미완료 항목을 회복 가능한 상태로 남긴다. |
| 통보 | 지원 여부·대기열 접수·전달·수신을 구분하고 실패 시 후속 인수 경로를 연결한다. |

담당 이름을 기록하는 것만으로 이 책임을 구현했다고 보지 않는다. 실제 실행
경로가 그 담당자에게 결속되고, 종료·재시작 뒤에도 의무를 되찾을 수 있어야 한다.

## 2. 표면은 단순하고 기본값은 교체 가능해야 한다

사용자와 에이전트는 목표, 입력, 작업 범위, 완료 조건을 표현한다. 경로·상태·
호출 순서·복구 명령의 조립은 하팅이 맡는다. 내부 계약을 지키기 위해 같은
내용을 여러 플래그와 문서에 반복 입력하게 만들지 않는다.

Capability와 recipe는 유용한 기본 구성이다. 모든 과제에 같은 단계를
강제하는 근거가 아니다. 계획·검증이라는 작업 단계와 별도 프로세스 분사는
분리한다. 독립 검토나 병렬 작업의 이득이 있을 때 분사하고, 허용된 직접
수행에서도 같은 결과·복구 책임을 지킨다.

모델·프로파일·용량 정책도 기본값이다. 쉬운 작업에 light를 선택할 수 있고,
명시적 선택은 지원되는 범위에서 반영한다. 인증, 실제 가용성, 승인 경계,
증거 무결성 같은 제약은 별도로 설명한다. 선택을 조용히 바꾸거나 단순한
preset 차이를 실행 불가능으로 만들지 않는다.

## 3. 공통 의미는 하나, 실행 수단은 하네스별로

Claude·Codex·OpenCode는 동등한 어댑터다. 입력, 완료, 재시도, 정리, 인수의
의미는 공통 계층이 소유한다. 프로세스 기동·재개·알림 수단은 런타임에 맞게
구현한다. 어느 하네스를 다른 하네스의 기준 구현으로 삼지 않는다.

지원하지 않는 운송을 지원한다고 표시하지 않는다. 가능한 대체 경로와
누가 다음 행동을 하는지까지 확인한다. 표면의 이름이나 원장 상태가 같다는
것은 동등한 책임 이행의 증거가 아니다.

## 4. 불확실성을 실패나 성공으로 꾸미지 않는다

관측할 수 없는 프로세스는 unknown이다. 다른 PID namespace에서 보이지
않거나 로그가 늦는다는 이유로 죽었다고 판정하지 않는다. 정체 경보 기한은
재관측·알림의 기한이지 작업 종료나 재시도 권한이 아니다. 긴 작업의 진척
기준은 workload가 선언하고, 일률적인 시간 상한으로 대체하지 않는다.

확정된 PASS와 FAIL은 보존한다. 이후 충돌은 현재의 소비를 보류할 수 있지만
과거 결과를 덮어쓰지 않는다. 후속 작업은 원본을 재작성하는 대신 정확한
lineage와 현재 증거를 연결한다. 기존 작업의 재사용은 새로운 검증 PASS를
만들어내는 행위와 구분한다.

## 5. 예외를 쌓기 전에 중복된 판단을 없앤다

수리는 실패를 낸 한 분기를 통과시키는 데서 끝나지 않는다. 동일한 결정을
하는 writer·reader·watcher·adapter를 찾아 공통 판정과 전이로 모은다. 새
경로가 기존 경로를 대체하면 중복 구현과 불필요해진 호출자 절차도 제거한다.
가드를 전부 없애거나 새 거부 규칙만 늘리는 방식으로 책임 공백을 숨기지 않는다.

문서는 동작을 설명하고 결정의 근거를 보존한다. 모델이 긴 운영 문서를
완벽히 기억해야만 정상 종료할 수 있는 프로토콜을 제품의 전제로 삼지 않는다.

## 6. 완료는 소비자 경로로 입증한다

수정 검증은 정상 완료뿐 아니라 지연된 결과, 중복 재시도, 관측 불가,
감독자 종료·재시작, 전달 실패와 담당자가 바쁜 경우를 다룬다. 해당 변경의
위험에 맞는 회귀를 선택하며, 등록이나 fixture 통과로 실제 수신을 대신
주장하지 않는다. 필요한 실측은 정확한 실행·결과·수신을 연결한다.

완료 보고에는 고친 행동, 없앤 중복 판단·수동 절차, 최종 책임자, 실제 검증과
미검증 경계를 담는다. 소스·릴리즈·설치본·실행 중 세션의 버전은 구분한다.
불필요한 모델 턴, 재기동, 수동 개입, 경계 대기 시간을 측정 대상으로 삼되
문서 크기나 코드 줄 수 감소를 토큰·비용 절감 실적으로 바꾸어 말하지 않는다.

## 근거와 현재 적용 범위

이 원칙은 2026-09-10~14 사용자가 반복 교정한 완료 기준을 정리한 것이다.
과거 구조 진단은 경계 비용과 모델에게 새는 운영 절차를 지적했고,
[책임 계약 수리 기록](../docs/dispatch-responsibility-repair.md)은 실제 완료와
실패를 함께 보존한다. 이 문서의 채택이 미수정 경로의 완성을 뜻하지 않는다.
개별 변경은 위 기준으로 입증해야 한다.
